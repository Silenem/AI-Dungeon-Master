# План разработки нулевой версии

Цель v0 — один игрок регистрируется, создаёт героя, самостоятельно проходит одно фэнтезийное приключение в браузере и может прервать игру с сохранением. Основной объём работы — реализовать предметы и действия в Go, связать их с ИИ-Мастером и подключить имеющиеся экраны.

[Исходный объём v0](v0-scope.md) · [Ролевая модель](role-model.md) · [Ход приключения](project-flow.md) · [Хранение данных](data-model.md)

## Интеграционный стенд `dev-release`

`dev-release` — ветка для совместной сборки фронтенда, Go-бэкенда и баз, развёртывания на dev-машине **INOAGENT** и сквозных тестов. Изменения приложения вливаются из рабочих веток фронтенда и `backend`. В `dev-release` храним настройки совместного запуска и проверяем интеграцию.

- **Один URL** — [c9e9d680.bspk.cc](https://c9e9d680.bspk.cc). По `/` отдаём фронтенд. Запросы на `/api/…` на том же домене проксируем в Go. Фронтенд обращается к API по относительным путям. Для маршрутов React отдаём `index.html` при прямом входе по ссылке и после обновления вкладки.
- **Один стек Docker Compose** на INOAGENT. Фронтенд и Go запускаются вместе с PostgreSQL, Redis и Elasticsearch. Go обращается к базам по именам сервисов в сети Compose. Для баз используем внутреннюю сеть и постоянные тома. Публичная точка входа обслуживает сайт и API.
- **Порядок развёртывания.** Собрать фронтенд и Go из `dev-release`, запустить базы, применить миграции PostgreSQL и проверить готовность API. Для подключения передать `POSTGRES_URL`, `REDIS_URL` и `ELASTICSEARCH_URL` с адресами сервисов внутри Compose. Параметры стенда и секреты подставляются из окружения INOAGENT.
- **Сквозная проверка.** По общему URL пройти вход, создание героя, запуск приключения, обычный ход и бой. Проверить возобновление сессии после обновления страницы и после перезапуска стека. Повтор подтверждённой команды сохраняет исход, а фоновая память доступна только в пределах нужного прохождения.

[Экспорт «Осиновый Брод»](setting-dark-fantasy.md) — пример пробного прогона модели на 8 млрд параметров без игровых сервисов. Интеграционный стенд нужен для следующей проверки, уже с Go и сохранениями.

### Готовность фронтенда к интеграции

- **Сборка.** В `frontend` и `auth` lockfile расходится с `package.json`. `npm ci` падает. После обновления lockfile во временной копии `vite build` проходит. В снимке `auth` линтер находит два неиспользуемых объявления.
- **Навигация.** Из текущей сборки открывается профиль и работает переключение темы. Прямые ссылки `/characters`, `/stories` и `/play` показывают профиль. Вход, персонажи и истории требуют регистрации маршрутов в React. Экран прохождения с чатом, видимой очередью боя и командами предстоит собрать.
- **Данные.** Создание героя, список и выбор истории открылись во временном маршрутизаторе. Отправка формы ведёт к статическому списку, а запуск истории открывает демосюжет без активного прохождения. В `src/api.js` пока шесть старых характеристик. Подключаем единый серверный справочник из четырёх характеристик, согласованные классы и снаряжение, затем регистрацию, создание и список героев, старт и возобновление прохождения.

## Предметы, инвентарь и экипировка

На старте выдаём один комплект по классу, всего три комплекта. У Бойца комплект из предметов, доступных обоим подклассам. Снаряжение для специализации герой добирает по ходу игры. До первого браузерного прогона нужно утвердить состав комплектов и права на экипировку. [Референсы D&D 2014 и предложенные комплекты](role-model.md#стартовые-комплекты-для-v0)

| Что сделать | Минимум для v0 |
| --- | --- |
| Справочник предметов | Завести стабильный `item_def_id`, название, категорию и правила применения. Наполнить предметами из стартовых комплектов и первого приключения. Для первого боевого теста достаточно определить снаряжение Бойца: копьё и чешуйчатый доспех. Остальной набор уточнить после выбора комплектов. |
| Оружие | Описать урон, число рук, боевые зоны и допустимые модификаторы. Развести разрешение атаковать и право получить прибавку от характеристики. Например, согласно рабочей модели, разрешённая атака Убийцы посохом использует +0, а подходящее фехтовальное оружие может получить бонус. Отдельный бонус мастерства остаётся открытым. |
| Доспехи и щиты | Указать категорию, базовый КД, правило учёта Ловкости, требования и помехи, актуальные для первого приключения. Щит даёт +2 к КД после экипировки. Задать права классов до специализации и стоимость смены экипировки в бою. |
| Расходники и боеприпасы | Определить, какие запасы считаются поштучно. Кандидаты для первого набора — стрелы и один предмет с одноразовым эффектом, если он нужен сценарию. Для стрел решить, тратится ли единица при выстреле, в том числе при промахе. Для любого расходника определить момент списания и допустимую цель. |
| Инструменты и сюжетные предметы | Описать, при каких условиях ключ открывает конкретный замок, а набор отмычек позволяет начать проверку. Для найденного предмета определить взаимодействие, источник выдачи и поведение при повторной попытке забрать его. Добыча и использованные предметы относятся к текущему прохождению. |
| Экземпляры и слоты | В инвентаре хранить `instance_id`, `item_def_id` и количество. В слотах хранить ссылки на экземпляры. Определить минимальные слоты для тела и рук, правила совмещения щита и одноручного оружия, требования двуручного оружия и объединения одинаковых расходников. |

Рабочий порядок операции в Go — найти экземпляр в текущем прохождении, проверить право на действие и допустимость цели, применить эффект и расход, сохранить единый результат. Например, щит из рюкзака сначала проверяется на доступность и свободную руку. После экипировки меняется КД. При попытке выстрелить из двуручного лука, пока рука занята щитом, сервер возвращает причину отказа. После загрузки те же ссылки на экземпляры дают тот же КД.

## Какие правила ещё нужно конкретизировать

| Узел | Решения перед реализацией |
| --- | --- |
| Первый бой | Порядок при равной инициативе, поведение одного NPC, условие начала и окончания боя. Движение, основное и бонусное действия и конец хода проверяет Go. В одиночном режиме при 0 хитов срабатывает согласованный хардкор. Начать с боя вплотную, затем определить стоимость переходов между зонами и диапазоны оружия. Вопрос об интерактивной карте вернётся после боевого теста. |
| NPC | Для первого противника взять данные SRD 5.1 и привести их к нашей модели. Определить минимальную карточку с КД, хитами, инициативой, атаками и правилами выбора действий. Отделить исходные параметры от текущих хитов, положения и отношения к герою. NPC могут появляться по ходу истории, их подтверждённое состояние хранит Go. |
| Проверки вне боя | После первого боевого теста выбрать небольшой набор действий, нужных сценарию. Например, проломить дверь Силой или открыть замок Ловкостью при наличии отмычек. Для каждого способа описать предпосылки, необходимость броска, сложность и последствия. Успех с ценой задаётся там, где предусмотрено конкретное осложнение. |
| Магия Мистика | Выбрать базовые заговоры и одно или два заклинания первого круга. Для каждого задать цель, дальность, тип действия, эффект и длительность. Заговоры стоят 0 ячеек, ячейки заклинаний по кругам списывает Go. Материальные компоненты в v0 опущены по принятому решению. |
| Прогрессия и подклассы | Решить, до какого уровня герой доходит в первом приключении и за какие результаты получает опыт. Зафиксировать уровни выбора подклассов. Если специализация доступна в v0, описать достижимые умения в отдельных таблицах с условиями, стоимостью, эффектом и восстановлением. Для Чародея отдельно задать варианты и цену метамагии и учесть расход бонусного действия. |
| Отдых и состояния | Определить, когда отдых возможен, сколько игрового времени занимает и что именно восстанавливает. Для состояний, которые реально используются в приключении, задать источник, эффект и момент снятия. |
| Глобальные события | Для одного приключения написать вступление и минимальные факты мира, затем задать проверяемые условия и последствия глобальных событий. Определить, какие действия продвигают игровое время и при каких фактах прохождение получает статус `completed` или `failed`. Смерть короля и сорванное покушение — два примера исхода, после которых Мастер может развить разные финалы. |

Для первого теста берём Бойца 1-го уровня с копьём и чешуйчатым доспехом против дозорного. Пользовательский старт использует утверждённый комплект класса и пустое поле подкласса.

## Порядок разработки

1. **Договориться о рамках первого приключения.** Определить условия завершения и максимальный достижимый уровень. Утвердить три стартовых комплекта и список предметов для одного боевого столкновения. Это определит, какие умения, эффекты и расходники попадут в первый проход.
2. **Собрать игровой модуль на Go.** Создание листа, версии справочников, инвентарь, экипировка, хиты и КД, затем инициатива и один бой вплотную. Проверить фиксированные броски, попадание и промах, смену раунда и смерть на 0 хитов. После этого добавить нужные сценарию проверки вне боя, применение предметов и минимальную магию.
3. **Подключить сценарий и ИИ-Мастера.** Описать контракт намерения, допустимые изменения мира и результат для рассказа. Go проверяет действия, бросает кубики, расходует ресурсы и применяет глобальные события. ИИ-Мастер интерпретирует свободный текст, уточняет неоднозначные запросы и рассказывает подтверждённый исход. Для первого прогона выбрать один рабочий API-адаптер из рассмотренных в `backend-LLM`.
4. **Подключить сохранения и память.** PostgreSQL хранит пользователей, героев, снимок с последним ходом и очередь обработки памяти. Redis ведёт активное прохождение. Elasticsearch хранит значимые фрагменты по ID сценария, прохождения, ходу и игровому дню. Сохранять по таймеру, после боя и при выходе. Повтор последнего запроса после восстановления должен вернуть прежний исход.
5. **Дать фронтенду согласованный API.** Параллельно с игровым модулем согласовать регистрацию и вход, справочник классов, создание и выбор героя, старт и возобновление прохождения, состояние игры и отправку команды. Подключить готовые экраны и добавить игровой экран со свободным вводом, подтверждённым исходом, видимой очередью боя и допустимыми боевыми командами.

## Приёмка

- [ ] Игрок регистрируется и создаёт героя каждого из трёх классов. Характеристики и стартовое снаряжение согласованы с серверным справочником.
- [ ] Попытка применить отсутствующий предмет отклоняется. Экипированный щит меняет КД, а занятая щитом рука исключает выстрел из двуручного лука.
- [ ] Игрок выполняет свободное действие и хотя бы один полный бой. Списание ресурсов, инициатива, хиты и исход отображаются по результату Go.
- [ ] Игрок закрывает браузер после команды и возвращается к сохранённому состоянию. Повтор последней команды сохраняет исход броска и количество ресурсов. Значимый ход попадает в память, в том числе если обработка завершилась после выхода.
- [ ] Один игрок доходит до финала без помощи разработчиков. Повторное прохождение с другим решением меняет исход глобального события и учитывает его последствия.
