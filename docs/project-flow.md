# Как работает приключение

Рабочая схема проекта. Go ведёт приключение и применяет правила. ИИ-Мастер понимает свободный ввод, запрашивает игровые проверки и описывает подтверждённый результат. Для генерации Go обращается по API к платному провайдеру или к модели, которую команда обслуживает сама.

## Где живут данные

| Хранилище | Какие данные хранит | Когда используется |
| --- | --- | --- |
| PostgreSQL | Пользователи, исходные листы персонажей, сохранённые прохождения и история ходов. | Go загружает данные при входе. При выходе из приключения сохраняет изменения после завершения активного взаимодействия. |
| Redis | Текущее состояние конкретного прохождения. Копия листа героя, сцена, хиты, предметы, ячейки, режим игры, недавние сообщения и очередь ходов в бою. | Go читает и обновляет это состояние во время игры. |
| Elasticsearch | Индекс значимых событий и фактов конкретного прохождения. | Перед новым ответом Go выбирает уместные воспоминания для контекста ИИ-Мастера. |

Ключ прохождения — `session_id`. Один пользователь может начать два прохождения с одним персонажем. У каждого прохождения будут собственные изменения листа и собственная память.

## Вход и выход

1. Пользователь открывает приключение. Go проверяет доступ и ищет уже активную сессию в Redis. Если она есть, продолжает с неё.
2. Если активной сессии нет, Go загружает последнее сохранение из PostgreSQL. Для нового прохождения создаёт в Redis копию выбранного персонажа и исходное состояние сценария.
3. В новом прохождении ИИ-Мастер показывает **заранее написанное вступление**. Go записывает его в историю один раз. При возвращении пользователь видит свою сцену и историю.
4. После ухода со страницы Go ждёт завершения активного ответа и переносит состояние и новые ходы из Redis в PostgreSQL. При следующем входе можно возобновить прохождение с последнего сохранённого момента.

## Обычный режим

1. **Игрок пишет сообщение.** Go передаёт ИИ-Мастеру текущую сцену, состояние героя, недавние реплики и найденные для этой ситуации воспоминания.
2. **ИИ-Мастер разбирает намерение.** Если действие требует проверки или меняет состояние, модель вызывает одну из доступных в текущем режиме игровых функций Go. В функцию передаётся намерение, например попытка открыть замок отмычкой. Go сам выбирает сложность, определяет исход и списывает ресурсы. Неясное намерение можно уточнить у игрока.
3. **Go разрешает проверку или действие.** Проверяет условия сцены и доступные предметы, при необходимости бросает кубик, применяет изменения к сессии в Redis и возвращает подтверждённый результат.
4. **ИИ-Мастер отвечает игроку.** Go сохраняет текст ответа вместе с ходом. После этого отдельная модель классифицирует завершённый обмен. Значимые факты идут в Elasticsearch, например обещание NPC, найденная улика или смена отношения к герою.
5. Игрок вводит следующее сообщение. Новый контекст составляется из текущего состояния и подходящих фактов.

## Боевой режим

Когда срабатывает условие начала боя, Go фиксирует участников и инициативу. В интерфейсе видны раунд, очередь, текущий участник и то, что ещё доступно на его ходу. Игроку доступны четыре команды.

| Команда | Что проверяет Go |
| --- | --- |
| **Перемещение** | Действует ли герой сейчас и хватает ли движения. После первого боевого теста определим представление позиций и дальности. |
| **Основное действие** | Осталось ли действие, доступен ли выбранный приём и допустима ли цель. Go разрешает атаку или другое основное действие по правилам. |
| **Бонусное действие** | Осталось ли бонусное действие и доступно ли соответствующее умение. Например, боевое применение метамагии расходует этот ресурс. |
| **Пропуск хода** | Герой завершает свой текущий ход и отдаёт очередь следующему участнику. Этой же командой заканчивается ход после уже выполненных действий. |

Интерфейс отправляет выбранную команду прямо в Go. Игрок может совместить движение и основное действие. Go списывает использованное движение и действия по мере выполнения. Он же определяет следующий ход, разыгрывает действия NPC и завершает бой по условиям сцены. ИИ-Мастер описывает события по готовым результатам, как и в обычном режиме. После боя Go возвращает интерфейс к свободному вводу. [Согласованные правила боя](role-model.md#раунд-ход-и-инициатива)

## Предлагаемые дополнения

1. **Обнаруживать выход на сервере.** Клиент может посылать сигнал выхода и периодически подтверждать, что страница открыта. Если клиент пропал, сервер считает сессию неактивной после тайм-аута. Для сохранения Go проверяет, что активный ход завершился. Обработчик закрытия вкладки иногда вообще не срабатывает, например когда мобильный браузер выгружают из памяти. [MDN о закрытии страницы](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)
2. **Добавить промежуточные сохранения.** Основной перенос остаётся при выходе. Предлагаю также сохранять после важных переходов, например завершения боя, и периодически при долгой игре. Между этими точками Redis стоит запускать с AOF и постоянным диском. При потере всего Redis восстановление идёт с последней записи в PostgreSQL. При стандартном AOF с синхронизацией раз в секунду авария может потерять последнюю секунду записей. [Сохранение данных Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
3. **Применять каждую команду один раз.** Go проверяет владельца сессии и её версию, допускает один активный ход для прохождения и атомарно пишет состояние и исход команды в Redis. Идентификатор запроса позволяет при повторе вернуть прежний бросок и результат. Если генерация прервалась после попадания, повторяется рассказ по сохранённому исходу. В PostgreSQL Go переносит снимок и историю вместе, сверяя версию. Данные Redis можно очищать только после подтверждённого сохранения той же версии и при закрытой сессии. [Транзакции Redis](https://redis.io/docs/latest/develop/using-commands/transactions/)
4. **Классифицировать память в фоне.** Предлагаю передавать классификатору реплику игрока, подтверждённый исход и текст ответа. На выходе нужны решение «сохранить» и короткие факты со ссылками на исходный ход. Индексацию можно повторить с тем же ID события. Если модель или Elasticsearch временно недоступны, задание остаётся в очереди, а игра продолжает работать с недавней историей. При закрытии прохождения незавершённые задания должны пережить очистку активной сессии.
5. **Начать с поиска по тексту и сущностям.** Для первой версии достаточно хранить в Elasticsearch `session_id`, `turn_id`, тип события, сущности и короткое описание. Фильтруем по текущему прохождению и подбираем несколько релевантных записей. Игровые факты вроде текущих хитов или наличия ключа Go читает из состояния сессии. Когда текстового поиска окажется мало, можно оценить поиск по embeddings на примерах из нашего приключения. [Фильтры Elasticsearch](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-bool-query) · [Поиск по нескольким полям](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-multi-match-query)

### Первый сквозной тест

Войти в подготовленную сцену у ворот и увидеть фиксированное вступление. Подать сообщение, разрешить его через игровую функцию и вызвать короткий бой вплотную. После ответа проверить запись значимого факта в память. Во время ответа на следующую команду закрыть страницу, дождаться сохранения и восстановить сцену. При повторе уже принятой команды хиты и очередь ходов должны совпасть с сохранённым результатом.
